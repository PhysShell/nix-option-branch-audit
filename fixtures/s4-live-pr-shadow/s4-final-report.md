## 13. `TOOL_ERROR` inventory

**1 entry, classified `attributable_to_unsupported_input: false` — a
confirmed hard failure.**

- **PR**: `#543492` (nixos/lightdm-enso-os-greeter: drop), S4-A cohort,
  position 117/120.
- **What happened**: this PR deletes
  `nixos/modules/services/x11/display-managers/lightdm-greeters/enso-os.nix`
  wholesale. The evaluation's own combined `targets.toml` named both
  the unaffected "lightdm" baseline target and the now-deleted
  "lightdm-enso-greeter" target — exactly `oba check --help`'s own
  documented rationale for making `--targets` resolve relative to the
  CWD rather than `--root` ("a manifest checked out once can later be
  pointed at two different roots (PR D: a base root and a head
  root)"), i.e. not a misuse of the CLI by this evaluation's own
  methodology, but the tool's own stated intended workflow.
  `oba check --root head-root --targets targets.toml --json` exits 3
  with EMPTY stdout and a single clean stderr line
  (`TOOL_ERROR: target lightdm-enso-greeter: module: resolving ...: No
  such file or directory (os error 2)`), losing ALL per-target results
  from that invocation — including the PASS for the entirely
  unrelated, unaffected "lightdm" baseline target, which had to be
  recovered via a separate, hand-constructed single-target supplemental
  manifest.
- **Independently reproduced** byte-for-byte by the coordinator
  directly against the frozen binary (not merely trusted from the
  data-gathering agent's own artifact).
- **Independently confirmed** that `oba audit-diff`, run over the exact
  same combined `targets.toml` against the same base-root/head-root
  pair, handles the identical condition gracefully (exit 2,
  `diff.kind="removed"` for the deleted target, correct unaffected
  report for "lightdm") — proving the tool's own design already
  anticipates a module vanishing at one of the two roots; `check`'s
  all-or-nothing abort is an inconsistency between the two subcommands
  under the tool's own documented base/head workflow, not a deliberate
  contract boundary.
- **Classification rationale** (full text in the ledger record's own
  `notes` field, reproduced in the S4-A batch 10 commit message): a PR
  deleting a NixOS service module is unambiguously ordinary, common
  nixpkgs activity, not an exotic or malformed input; the practical
  consequence — one deleted, unrelated target silently destroying ALL
  other targets' results in the same manifest/root invocation, with no
  partial recovery short of hand-constructing a supplemental manifest —
  is a real robustness gap for any CI/batch usage of `check` across an
  evolving PR history.
- **This is a tier-1 hard failure** under protocol.md's own frozen gate
  precedence ("a `TOOL_ERROR` on an ordinary supported input"), and
  drives the final gate result in item 18 regardless of the otherwise
  strong precision numbers.

No other TOOL_ERROR occurred anywhere in S4-A or S4-B (all other
non-zero exit codes across all 94 applicable PRs were ordinary
Inconclusive-class exit code 2, with well-formed JSON output and empty
stderr — not crashes).

## 14. `INCONCLUSIVE` root-cause breakdown

9 total inconclusive instances across the full ledger
(`inconclusive_count` field sum), 9.57% of processed positions
(`inconclusive_rate`), across 7 distinct root causes:

1. **Nested 2-segment dotted-key option declaration** (`options.services
   = {pixelfed = {...};};`) bypasses both `scan_options` entry-point
   shapes — `discovered_options` empty despite real `enable`/`package`/
   `user`/`group` declarations existing (`#526840` pixelfed, S4-A —
   see also item 17).
2. **Let/alias-resolution limitation**: test node is a let-bound
   function reference (`TestConfigUnresolved`) — 2 instances.
3. **Runtime-only predicate consumption**: real declaration found but
   no Nix-level branch consumes it (only read at runtime by the
   daemon) — an honest `PredicateNotFound`, not a tool defect.
4. **Dotted-LHS declaration shape** (`options.services.cloudlog = with
   types; {...}`) — the predicate-side walker DOES find the real
   `mkIf cfg.enable` usage, only the declaration-side walker misses it
   in this shape (`#399257` cloudlog, S4-A — see also item 17).
5. **Non-standard `installed-tests` harness shape** the test-config
   walker can't parse (`nixos/tests/installed-tests/pipewire.nix`) —
   honest fail-closed, not a false anything.
6. **Wildcard `attrsOf(submodule)` target** (`option_prefix
   [...,'services','*']`) — `discovered_options=0` despite real
   `mkOption` declarations existing at head for both watched options,
   the same general wildcard-prefix shape this project's own `kimai`
   fixture uses successfully elsewhere; root cause not diagnosed this
   round (`#411705` gitlab-runner, S4-A, and independently re-observed
   at `#507312` frp, S4-B batch 6 — confirmed recurring, not a one-off;
   see item 17).
7. **Non-boolean top-level predicate**: module has no top-level
   `enable` option; the real gate is `mkIf (cfg.networks != {})`,
   `networks` watched as a mechanical stand-in — `PredicateNotFound`
   both sides, a nonstandard non-boolean predicate shape not evaluated
   for correctness this round.

`origin_unclear_count`: 0 across the entire ledger (the one
`origin_unclear`-labelled transition, `#524479`, was a `new_finding`
correctly counted under item 12's causal-framing review, not double-
counted here).

## 17. Newly discovered gaps, not implemented

Three genuinely new tool-discovery gap classes surfaced during S4-A,
none acted on (per the standing instruction that S4 findings are
evidence for a future decision, never authorization for `src/` fix
work during the evaluation itself):

1. **`#526840` (pixelfed)** — nested 2-segment dotted-key option
   declarations (`options.services = { pixelfed = {...}; };`) are
   invisible to `scan_options`'s discovery walk; the module has real
   `enable`/`package`/`user`/`group` declarations that a maintainer
   would expect the tool to see.
2. **`#399257` (cloudlog)** — a dotted-LHS declaration shape
   (`options.services.cloudlog = with types; {...}`) is asymmetrically
   handled: the *predicate*-side walker correctly finds the real
   `mkIf cfg.enable` usage, but the *declaration*-side walker misses
   the same option in this shape — an internal inconsistency between
   the tool's two walkers on the identical module.
3. **`#411705` (gitlab-runner)** and **`#507312` (frp, S4-B)** —
   `discovered_options=0` for a wildcard `attrsOf(submodule)` target
   (`option_prefix [...,'services','*']`) despite real `mkOption`
   declarations genuinely existing at head for the watched options in
   both cases. This is the same general wildcard-prefix shape the
   project's own `kimai` fixture already uses successfully elsewhere —
   observed independently twice, in two different modules, across two
   different cohorts, confirming this is a real, recurring gap class
   rather than a one-off artifact. Root cause not diagnosed this round.
