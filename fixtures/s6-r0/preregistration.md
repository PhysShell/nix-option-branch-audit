## 1. Scientific question

> On a genuinely fresh set of `NixOS/nixpkgs` changes that played no
> role in S5, its remediation, test construction, or acceptance, does
> released `v0.5.0` produce materially incorrect maintainer-facing
> conclusions that reveal defect classes not already represented by
> the accepted test/frozen corpus?

The target is **unknown failure modes**. Known residual limitations
may appear naturally; S6 is not designed around finding them (see item
15).

## 2. Anti-overfitting / leakage prevention

The fresh corpus must not contain any PR used in historical S5,
adjudication, F1/F1B/F1C/F1D/F1D-R/F2/F2-R/F3/F3-R, or any synthetic
fixture derived from those PRs.

**Mechanical exclusion list**: `fixtures/s6-r0/excluded-pr-identities.json`
(generated by `fixtures/s6-r0/build-exclusion-list.py`, already run —
see that file's own header for why the 369-PR S5 ledger alone is
provably sufficient: every PR number touched by any remediation round,
including every "additional sound correction" the `-R` rounds
themselves discovered, is provably a member of this one ledger, since
every round's own replay pipeline only ever operated on the frozen,
independently-re-derived-and-confirmed-identical applicable-manifest
descending from it).

**Structural argument, stated for transparency, not relied on alone**:
GitHub PR numbers are monotonically increasing and never reused. Every
S5 PR number is ≤ 558042 (the ledger's own maximum). A PR that is
genuinely, freshly merged after the `v0.5.0` release date is
structurally incapable of colliding with a historical S5 PR number.
This makes overlap effectively impossible by construction — but the
mechanical diff (`check_leakage` in `population-and-sampling.py`)
still runs as a real, cheap, belt-and-suspenders check, not skipped
merely because the argument sounds convincing.

**If overlap is ever found**: excluded mechanically, and the frozen
sampling rule (seeded shuffle, next-in-order) supplies a replacement —
never a manually hand-picked substitute.

## 3. Temporal freshness

**Lower bound**: `2026-09-24T05:46:05Z` — the exact `publishedAt`
timestamp of the `v0.5.0` GitHub Release (`gh release view v0.5.0
--json publishedAt`), not the tag-push time (`05:43:03Z`) or the
release commit's own commit time (`05:24:46Z`). Rationale: this is the
literal moment the software became publicly available as `v0.5.0` —
the earliest moment a "post-release" nixpkgs change could exist in any
meaningful sense.

**Initial upper bound**: lower bound + 7 UTC days =
`2026-10-01T05:46:05Z`.

**Extension rule** (frozen, mechanical, never manually chosen because
an interesting PR appears nearby): if the P0 census of the current
window finds fewer than **20** `potentially_relevant` PRs (NC1, below)
among the inspected subset, extend the upper bound by a further whole
**+7 UTC days** and re-run the FULL census over the new, larger
window from scratch (not incrementally) — because the census inspects
an evenly-spaced systematic sample across the WHOLE window (see
`population-and-sampling.py`'s own `systematic_sample`), not merely
its earliest slice, so growing the window changes what gets inspected,
not just how much. Repeat until either the threshold is met, or the
window would exceed a **hard cap of 42 UTC days** total from the lower
bound, at which point S6 KILLs under NC1 (`STOP_LOW_YIELD`) with the
window frozen at its final, failed state and the actual count reported
— no further extension "just to see."

**Why +7/42, not a number derived from actually checking nixpkgs**:
`nixpkgs` is a very large, famously high-traffic monorepo; a one-week
window is expected, on general knowledge of the project's own scale,
to already contain far more than enough raw merged-PR volume for this
pilot's own tiny needs. This estimate is NOT the result of querying
nixpkgs for its own current PR volume in this specific window (that
would itself be a P0 activity, forbidden in R0) — it is a
cost/reasonableness judgment about window SIZE, made without looking
at the actual candidate population's own content or count. The
mechanical extension rule is the real safety net regardless of whether
this estimate is right.

## 4. Population and cheap relevance filter

**Population**: PRs merged into `NixOS/nixpkgs`'s `master` branch
within the frozen window (UTC), ordered ascending by `merged_at`, ties
broken by PR number ascending. Backport PRs targeting a stable release
branch are excluded by this same `base:master` rule — a mechanical,
branch-metadata criterion, never a title/label read. Reverts are
INCLUDED as ordinary merged PRs (excluding them would require reading
PR content/title, forbidden). No multi-PR-series collapsing — each
merged PR number is its own independent unit.

**Cheap relevance filter** (metadata-only, changed-file paths alone —
reused verbatim from historical S5's own two base signals, see
`fixtures/s5-design/extract-features.py`'s own `module_files`/
`test_files`, not an invented new criterion):

- `potentially_relevant`: at least one changed file starts with
  `nixos/modules/` or `nixos/tests/`.
- `obviously_irrelevant`: neither.

No filtering by title, label, migration-helper keyword, `imports=`,
wildcard pattern, or any other analyzer-specific feature (per item 4's
own explicit prohibition).

## 5. Kill-first protocol

### 5.1 What must be true for S6 to be worthwhile

1. Fresh nixpkgs development produces enough potentially applicable
   PRs.
2. The existing target-construction protocol can generate analyzable
   cases without large amounts of manual invention.
3. The resulting cases produce enough nontrivial outputs to adjudicate.
4. Independent review can establish a useful correctness oracle for at
   least a subset.
5. Expected information gain exceeds the cost of another large
   S5-style exercise (S6's own pilot is designed to be far cheaper
   than S5 specifically so this condition is easy to satisfy even for
   a modest information gain).

### 5.2-5.4 Necessary conditions, falsifiers, and frozen KILL criteria

| # | Necessary condition | Cheapest falsifying observation | Frozen KILL threshold |
|---|---|---|---|
| NC1 | Applicability density | P0 census of the (possibly window-extended) sample shows too few relevant PRs | **< 20** `potentially_relevant` PRs among ≤100 systematically-sampled census records, even at the 42-day window cap → `STOP_LOW_YIELD` |
| NC2 | Target derivability | Most of the P1 sample requires manual target invention beyond the frozen protocol | **< 9 of 15** P1 PRs reach step 6 of `target-construction-protocol.md` (a successful mechanical derivation) → `STOP_HARNESS_FAILURE` |
| NC3 | Analyzable yield | Most targets fail before meaningful analysis for reasons unrelated to correctness | Of the PRs with a derived target, **< ⌈0.7×n⌉** reach a substantive `oba` result (not `INPUT_OR_HARNESS_FAILURE`) → `STOP_HARNESS_FAILURE` |
| NC4 | Adjudicability | Reviewers repeatedly can't decide from source/test evidence | Of the substantive-result cases, **< ⌈0.7×n⌉** are adjudicable (i.e. more than ~30% `ORACLE_AMBIGUOUS`) → `STOP_ORACLE_FAILURE` |
| NC5 | Novelty opportunity | The pilot is dominated by exact structural repeats of S5 fixtures | **Qualitative, not independently KILL-gated** — see below |

**NC5 is deliberately not given an independent hard numeric KILL**, per
item 5's own instruction not to require novelty in every case. A hard
number here would invite exactly the "adjust the rule until it agrees
with what we want" failure mode this preregistration exists to
prevent for a criterion that is inherently harder to operationalize
cleanly than NC1-4. Instead: the decision gate (section 10) folds NC5
into the qualitative EXPAND/STOP judgment directly — if literally 100%
of adjudicable cases are structurally identical to a documented S5
pattern, that fact is reported honestly as part of the decision, not
hidden, but it does not mechanically abort the pilot on its own the
way NC1-4 do.

**Discipline**: once a KILL threshold is crossed, the pilot stops.
"Let's just check a few more PRs" is explicitly not an option this
round authorizes.

### 5.5 Pilot budget (operational quantities, not the eventual full S6)

- Maximum raw PR metadata records inspected for changed files (P0
  census, across all window-extension attempts): 100 per window-check
  × up to 6 window-checks (7/14/21/28/35/42-day windows) = **600
  maximum**.
- Maximum PRs advanced to P1 sampling: bounded by the census's own
  `potentially_relevant` output at whichever window-check first meets
  NC1 (no separate cap beyond that).
- P1 sample size: **exactly 15**.
- Maximum reviewer decisions (primary): **15** (one per P1 PR that
  reaches a substantive result or an explicit non-substantive
  classification).
- Maximum secondary-reviewer escalations: bounded by the primary set
  (≤15), triggered only per the frozen rule in `adjudication-rubric.md`
  — no separate cap needed since escalation is rare by the rule's own
  design.
- Maximum fetch/rerun attempts: **3 per file** before a PR's own
  target/result is marked `window_evaluation_incomplete` /
  `INPUT_OR_HARNESS_FAILURE` (see item 17).
- Maximum manual source inspections: bounded to the 15 P1 PRs' own
  base/head module+test files — a small, fixed number.

This pilot is deliberately far cheaper than historical S5's 369-PR
program.

## 6. Sampling rule

**Method**: deterministic seeded shuffle (Option B), same convention
historical S5 itself used (`fixtures/s5-design/s5-protocol-final.md`:
`seed = int("8f1701a", 16)`, the historical analyzer's own commit short
SHA) — here, `seed = int("0a6f192", 16)`, the **released `v0.5.0`
commit's own short SHA**. This value is fixed and public before any
candidate population exists; it cannot be chosen to favor any
particular sample.

**Procedure** (fully specified in `population-and-sampling.py`,
committed but not executed): `random.Random(seed).shuffle(pool)` over
the final, successful window-check's own `potentially_relevant` list;
first 15 taken as the P1 sample.

**Deduplication**: by PR number. **Backport/cherry-pick handling**:
excluded upstream by the `base:master` population rule (section 4), no
separate handling needed downstream. **Revert handling**: included,
no special-casing. **Multi-PR series handling**: none — every PR
number is independent.

## 7. Staged design

`metadata census (P0)` → `tiny OBA pilot (P1)` → `bounded adjudication
(P2)` → `decision whether a larger S6 is justified (section 10)`.

No jump directly to a large frozen corpus "because 369 has acquired
ceremonial significance" (explicitly rejected, per the mandate's own
framing).

## 8. Pilot size (frozen, not merely illustrative)

- **P0**: census, ≤100 changed-file inspections per window-check,
  metadata only, no `oba` execution.
- **P1**: exactly **15** mechanically-sampled `potentially_relevant`
  PRs; frozen target construction per
  `target-construction-protocol.md`; run released `v0.5.0`.
- **P2**: blind adjudication of every substantive P1 result (PASS,
  inconclusive, and finding-class outcomes alike — never findings
  only), per `adjudication-rubric.md`.

## 9. Preventing result-dependent target selection

Enforced structurally by `target-construction-protocol.md`'s own
step ordering: steps 1-6 (diff inspection, target freezing) happen
strictly before step 7 (`oba` execution). No step permits looking at
`oba`'s own output before the target record is frozen and written.

## 10. Decision gate after the pilot (frozen before results)

- **EXPAND** — pilot passed NC1-4, adjudication was practical, and at
  least the qualitative NC5 bar (some real novelty opportunity) was
  met → justifies a larger, separately-preregistered S6 frozen corpus.
- **STOP_LOW_YIELD** — NC1 KILL.
- **STOP_ORACLE_FAILURE** — NC4 KILL.
- **STOP_HARNESS_FAILURE** — NC2 or NC3 KILL.
- **STOP_DEFECT_FOUND** — **frozen now, per item 20's own explicit
  instruction to decide this before discovering one**: if the pilot
  produces even ONE case independently classified `FALSE_FINDING` or
  `MISSED_FINDING` (a confirmed, Tier-1-style analyzer defect, per the
  strict "new defect" definition in `adjudication-rubric.md`), S6
  STOPS expansion immediately and moves directly to a SEPARATE,
  future remediation preregistration (an "S6-F1-style" line, exactly
  mirroring how S5's own three confirmed defects each got their own
  independent fix/acceptance line) — it does NOT continue collecting
  more pilot cases "while we're at it," and it does NOT patch the
  analyzer as part of S6 itself (item 16).

A discovered real defect is a **successful** experiment outcome, not a
failed one (item 19) — `STOP_DEFECT_FOUND` is not a failure mode
alongside `STOP_LOW_YIELD`/`STOP_ORACLE_FAILURE`/`STOP_HARNESS_FAILURE`;
it is the pilot doing exactly its job.

## 11. Larger-S6 expansion rule (specified now, not executed)

If `EXPAND` is reached, the larger corpus size is chosen by an
**information/cost target**, not a copy of S5's own 369-PR count:
**sequential bounded design** — continue sampling (same seeded-shuffle
convention, next unused indices) and adjudicating in fixed batches of
15 (matching the pilot's own unit), stopping the FIRST time either (a)
a cumulative total of **30 adjudicated substantive cases** is reached,
or (b) **3 consecutive batches** each independently satisfy NC1-4 at
the SAME thresholds already frozen here, whichever comes first. This
mirrors the historical S5 protocol's own precedent of a
distinct-count-or-cap stopping rule
(`fixtures/s5-design/s5-protocol-final.md`'s own "stop at 30 distinct
actionable PRs or the cap, whichever comes first") rather than
inventing a new one. The exact batch count/cumulative target is
decided in THIS document, not adjusted after seeing how the pilot
turns out.

## 12. Comparison to historical S5

S6 does not attempt to reproduce, and will not report, a comparative
defect-rate claim like "v0.5.0 is N times better than v0.4.5" — the
two populations (S5's own historical frozen sample vs. S6's fresh
post-release sample) are not drawn under a comparable design, and S5
measured a different, earlier build. S6's own primary purpose is fresh
correctness discovery on the CURRENT release, not a marketing
statistic.

## 13. Known-limitations challenge set

**Decision: not run in S6-R0.** The primary pilot's own sampling frame
(section 4/6) deliberately excludes any keyword/pattern-based
selection for `imports=`, wildcard collisions, cross-instance
ambiguity, `listOf`, flat-dotted declarations, or wrapped-root cases —
these must never contaminate the primary out-of-sample estimate. A
SEPARATE challenge-set preregistration may be written later, after
this primary design remains frozen and unchanged; its own results, if
ever run, would be reported separately and never merged into the
primary yield/defect-rate numbers.

## 14. Fetch/infrastructure discipline (item 17)

- GitHub rate limit hit mid-census/pilot: back off and retry per
  `gh`'s own standard rate-limit handling; if still blocked after 3
  attempts for a given call, mark that call's own subject
  `window_evaluation_incomplete` and continue with the rest of the
  batch — never silently skip without recording the reason.
  window and continue with the rest of the batch — never silently
  skip.
- Deleted/force-pushed ref, unavailable merge-base, fetch failure,
  parser crash, missing test/module file: all classify as
  `INPUT_OR_HARNESS_FAILURE` for that specific target (not
  `MISSED_FINDING`, not silently dropped).
- Any PR where the ENTIRE target-construction or `oba` run could not
  complete after the 3-retry budget (section 5.5): recorded as
  `window_evaluation_incomplete`, kept in the fixed 15-PR denominator,
  never replaced with a substitute PR.

## 16. Analyzer immutability (item 16)
