# C-E1.1: executable-fit qualification audit for a future `GeneratedConfigArtifact` CDC abstraction

Not a coding round. A qualification gate. The question: does E1's own
35%-of-holdout signal ("a generated multi-key config file gets read
back") survive being turned into a mechanically checkable claim two
independent reviewers agree on -- or does it dissolve into "well, it
kind of looks like it" the way the CDC fit rubric's own 50% inter-rater
disagreement already showed generic "existing abstraction vs. new
adapter" judgments can?

**Zero `src/` changes anywhere in this round.** Protocol, evidence, A/B/C/D
judgments, independent review, disagreement report, conclusion -- no
Rust.

## The executable fit criterion

A candidate qualifies for a future `GeneratedConfigArtifact` abstraction
only if all FOUR links are separately proven, each with its own cited
evidence -- never inferred from the others, never "mostly yes":

```
Nix producer
    |
    | A. produces the exact artifact
    v
generated config artifact
    |
    | B. that SAME artifact is bound to the consumer process
    v
consumer invocation
    |
    | C. the exact pinned consumer's own source parses it
    v
consumer configuration model
    |
    | D. the accepted keys/paths can be extracted
    v
consumer contract
```

**A. Producer ownership.** Mechanical proof the artifact is really
generated by the Nix module -- `pkgs.writeText`/`writeTextFile`,
`environment.etc`, `systemd.tmpfiles`, a `format.generate` call
(`pkgs.formats.{json,yaml,toml,ini}`), or an equivalent real generated
derivation. Must yield either the exact real store path pattern or the
exact real rendered content (via `nix eval`, not read off the module
source by eye). "the module source mentions `/etc/foo/config.yaml`
nearby" does NOT count.

**B. Artifact binding.** Mechanical proof the SAME artifact is what the
consumer process actually receives -- `ExecStart = "... --config
${configFile}";`, `Environment = "FOO_CONFIG=${configFile}";`, or an
equally unambiguous binding, with the SAME real store-path/content
identity as A's own answer, not merely a filename that looks similar.
This is the one E1 itself never checked (its CDC classifications were
producer-structure-only) -- and the one most likely to quietly fail
(a config file can be generated and never actually read).

**C. Consumer reachability.** From the consumer's own real, exact
pinned upstream source (fetched at the real version the Nix package
pins, same discipline as every K1-K5 vendoring round): a real,
traceable path from the CLI flag/env var/default path the binding in B
uses, through to an actual parser call for the artifact's format --
`--config -> loadConfig(path) -> yaml.Unmarshal(...)`, or an equivalent
named library/schema use. `extension == ".yaml"` alone does not count.

**D. Contract extractability.** Only decided once A-C are proven: can
the accepted keys/paths actually be extracted from the consumer's own
source in a BOUNDED way -- a declared schema, a typed config struct with
serialization tags, or a bounded set of explicit parser field accesses?
If the consumer deserializes into a formless `map[string]any`/`dict`/
freeform table and scatters it through arbitrary later code, that's
`CONTRACT_UNEXTRACTABLE`, even if A-C are perfect.

**Fit = A && B && C && D. No partial credit, no "supported with a
little more work."** A-C true, D false is reported as `NOT CURRENTLY
EXECUTABLE`, not "almost there."

## Reason codes (fixed before any candidate is inspected)

```
SUPPORTED              -- A && B && C && D, real fit
NO_PRODUCER_PROOF      -- A fails
NO_ARTIFACT_BINDING    -- A holds, B fails
CONSUMER_UNRESOLVED    -- A && B hold, C fails
CONTRACT_UNEXTRACTABLE -- A && B && C hold, D fails
```

## Recording schema, per candidate

```
candidate:
A_producer: proved | no | inconclusive   (+ evidence: store path / rendered content, real nix eval)
B_binding:  proved | no | inconclusive   (+ evidence: real ExecStart/Environment= string)
C_consumer: proved | no | inconclusive   (+ evidence: real source file:line, exact pinned version)
D_contract: proved | no | inconclusive   (+ evidence: schema/struct/bounded accesses, real source citation)
fit: yes | no
reason_code: SUPPORTED | NO_PRODUCER_PROOF | NO_ARTIFACT_BINDING |
             CONSUMER_UNRESOLVED | CONTRACT_UNEXTRACTABLE
notes:
```

## Independent review, done better than E1's own first attempt

A second reviewer gets ONLY the criterion above plus the raw evidence
(real source citations, real nix-eval output) -- never the first pass's
A/B/C/D verdicts or reason codes. Agreement is measured PER LINK
(A/B/C/D separately), not on a single vague "fits or doesn't" bucket --
`{A=yes,B=yes,C=yes,D=no}` matching on all four axes is a categorically
stronger signal than both reviewers independently saying "needs an
adapter." If agreement jumps sharply from E1's own 50% once the
criterion is this concrete, that's itself the qualification result. If
it's still ~50%, the abstraction stays a concept, not a specification,
and no code gets written regardless of the raw fit count.

## Decision rule, fixed before any candidate is inspected

```
if >= 5 of 14 show A && B && C && D
   AND inter-rater agreement >= 80% (per-link):
      -> build C-E1.2 / GeneratedConfigArtifact vertical

if A && B && C hold often, but D fails often:
      -> bottleneck is CONSUMER CONTRACT EXTRACTION,
         not the producer-side abstraction -- named as the real
         next problem, not "config file support"

if B or C fail often:
      -> the generated-config abstraction itself is too broad --
         "generated config file" was never one boundary

if support is spread across several formats (JSON/YAML/TOML/HCL/INI/...)
   but the EVIDENCE CHAIN (A->B->C->D) is the same shape throughout:
      -> strong universality signal -- format is a locator detail,
         never its own abstraction variant (see below)
```

## What the abstraction is NOT, decided before any evidence is looked at

Format does not define the abstraction. `YamlEvidence`/`TomlEvidence`/
`JsonEvidence`/`IniEvidence` as separate architectural variants are
explicitly rejected before this audit starts -- the target shape, if
qualified, is roughly:

```
GeneratedConfigArtifactEvidence {
    producer,       // A
    artifact,       // A's own real identity (path/content)
    binding,        // B
    format,         // which parser/locator this specific case needs
    emitted_paths,  // D's own result
}
```

JSON/YAML/TOML/HCL/INI/Elixir-conf/bash-array are ways to GET
`emitted_paths` (format-specific locators), never separate evidence
models. If this audit finds the A->B->C->D chain holds the same way
across several different formats, that's the actual proof a reusable
abstraction exists underneath the format variety -- a `FormatAdapter`
trait/dispatch feeding one evidence type, never five near-identical enum
variants that exist because humans invented five ways to write braces.
