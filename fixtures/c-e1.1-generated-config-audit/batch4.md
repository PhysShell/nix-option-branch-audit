## unbound

- **A_producer**: proved -- a hand-rolled Nix serializer (`toConf`, module.nix:12-31), NOT a `pkgs.formats.*` call, but still a real generated derivation: `confFileUnchecked = pkgs.writeText "unbound.conf" ''...'';` (module.nix:40-47), optionally wrapped through a real `unbound-checkconf`-validating derivation if `cfg.checkconf` (module.nix:48-67). Real eval confirms `environment.etc."unbound/unbound.conf".source` = `/nix/store/z6ys8079px2y26b2dg4046zjd11sg5kk-unbound.conf`.
- **B_binding**: proved, but via a MEANINGFULLY DIFFERENT mechanism than unpackerr's direct case -- `ExecStart = "${cfg.package}/bin/unbound -p -d -c /etc/unbound/unbound.conf";` (module.nix:309) does NOT reference the store path directly; it references the fixed `/etc/unbound/unbound.conf`, which is populated by `environment.etc."unbound/unbound.conf".source = confFile;` (module.nix:282), a real, separate NixOS activation-time mechanism (a symlink/copy created at system activation, not baked into the command line). Real eval confirms `ExecStart` = `".../unbound-1.26.0/bin/unbound -p -d -c /etc/unbound/unbound.conf"` and the `environment.etc` source resolves to the SAME real store path as A's own artifact. Proved, but flagged: a `GeneratedConfigArtifact`'s own `binding` field needs to represent BOTH "direct store path on the command line" (unpackerr) AND "indirect via a fixed `/etc` path populated by `environment.etc`" (unbound) as real sub-shapes of the same B link, not just one.
- **C_consumer**: proved -- real upstream `NLnetLabs/unbound` at tag `release-1.26.0` (commit `a45da353d3feb5d8fc00685fa1ceda3816d5108f`, matching the real pinned `1.26.0`). `daemon/unbound.c:783`: `case 'c': cfgfile = optarg;` (`-c` flag parsing). `daemon/unbound.c:697`: `config_read(cfg, cfgfile, daemon->chroot)` -- a real named parsing function (`util/config_file.c`, a real yacc/lex grammar over `util/configparser.y`).
- **D_contract**: proved -- `util/config_file.h:72`, `struct config_file { int verbosity; int stat_interval; ...}` -- a large (hundreds of fields) but genuinely fixed, named, typed C struct, parsed via a real grammar referencing each field by name. Bounded, just LARGE.
- **fit**: **yes**
- **reason_code**: **SUPPORTED**
- **notes**: the real, useful complication this candidate adds: B's own real mechanism (indirect via `environment.etc`, not a literal command-line path) is a second, equally real, equally provable binding SHAPE the future evidence model needs to represent -- not a reason to fail B, but a reason `binding` can't be modeled as "always a literal substring of ExecStart."

## mobilizon

- **A_producer**: proved -- `settingsFormat = pkgs.formats.elixirConf {...}; configFile = settingsFormat.generate "mobilizon-config.exs" cfg.settings;` (module.nix:24-26), a real Elixir-conf-format-generating derivation.
- **B_binding**: proved, a THIRD distinct real sub-mechanism -- neither a direct ExecStart flag nor an `environment.etc` symlink, but a `makeWrapper`-generated launcher script: `makeWrapper $src/bin/mobilizon $out/bin/mobilizon --set MOBILIZON_CONFIG_PATH "${configFile}" ...` (module.nix:40-45), and `ExecStart = "${launchers}/bin/mobilizon start";` (module.nix:301) runs the WRAPPED binary, which sets the `MOBILIZON_CONFIG_PATH` env var (to the SAME real `configFile` derivation) before exec'ing the real mobilizon binary. Real, mechanically checkable (the wrapper script's own generated content directly embeds the `configFile` store path), just a third concrete shape.
- **C_consumer**: proved -- real upstream `framasoft/mobilizon` (hosted on framagit.org/GitLab, not GitHub -- confirmed via `mix.exs`'s own `source_url`) at real tag `5.2.4` (commit `e4e3d70747e1214415540eceb2bafeefabf0695c`, matching the real pinned `5.2.4` from `pkgs.mobilizon.version`). `mix.exs:33`: `config_providers: [{Mobilizon.ConfigProvider, "/etc/mobilizon/config.exs"}]`. `lib/config_provider.ex`: `config_path = System.get_env("MOBILIZON_CONFIG_PATH") || path` then `Config.Reader.read!(config_path)` -- Elixir's own standard `Config.Reader` (a real, named parser for `.exs` config files), then `Config.Reader.merge(config, runtime_config)`. A clean, complete, real chain from the exact env var B sets to the exact parser call.
- **D_contract**: proved, but genuinely borderline -- flagged explicitly for the blind reviewer to independently weigh. `Config.Reader.read!` parses into Elixir's generic, dynamic `Application` config registry, not one single struct -- there is no ONE schema covering the whole surface. However: (1) `lib/mobilizon/config.ex` DOES declare a real, bounded `@type mobilizon_config :: [name: String.t(), hostname: String.t(), ...]` typespec for the `:instance` config group (matching Nix's own `":instance"` option group exactly); (2) the OTHER config groups Nix exposes (`Mobilizon.Web.Endpoint`, `Mobilizon.Storage.Repo`) are consumed via Phoenix's and Ecto's own STANDARD, well-documented, bounded config-key conventions (not custom to mobilizon, but not freeform either). Marked `proved` on the judgment that "bounded, via app-specific typespecs plus standard, well-known library schemas" still counts as extractable -- but this is exactly the kind of borderline call E1's own blind review process exists to catch, and is flagged here explicitly rather than smoothed into a confident "yes."
- **fit**: **yes** (borderline on D, see above)
- **reason_code**: **SUPPORTED**
- **notes**: mobilizon required by far the most real research this batch -- mix.exs's `config_providers` mechanism and the actual `Mobilizon.ConfigProvider` module (at the non-obvious path `lib/config_provider.ex`, NOT under `lib/mobilizon/`) were not discoverable from the Nix module alone; needed real upstream source search. A genuinely strong confirmation that C requires real per-app research, not a generic "check the docs" shortcut.
